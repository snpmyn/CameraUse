## CameraUse

摄像头应用

## 原理

普通相机应用和扫码应用的本质区别，只在于图像数据的最终去向（消费者）不同：

                 ┌─► 画面渲染层 (TextureView / SurfaceView)  ──► 【普通相机 App：只看展示】
 USB 摄像头流 ───┤
                 └─► 内存字节数组 (byte[] NV21) ──► ZXing 解析 ──► 【你的扫码 App：数据解码】
				 
                        ┌─► 1. 传给 SurfaceView / TextureView ──► 【屏幕上看到实时预览画面】
USB 摄像头输出数据流 ───┤
                        └─► 2. 传给 ZXing (IFrameCallback) ──► 【后台解析二维码，屏幕看不到】
						
                    ┌─► 1. 华高原生扫描仪 ──(官方 SDK)──► 负责把 A4 纸/文件扫描成高精 Bitmap
华高设备 Android 系统 ┤
                    └─► 2. 外接 USB 摄像头 ──(UVCCamera)──► 负责拉取视频流抛给 ZXing 扫码

  │ 你的业务代码 (扫码、拍照、UI 界面)                      
  └───────────────────────────┬─────────────────────────────┘
                              │ 调用封装 API
  ┌───────────────────────────▼─────────────────────────────┐
  │ 4. AndroidUSBCamera (开箱即用的高级框架)                  
  └───────────────────────────┬─────────────────────────────┘
                              │ 内部组合协调
            ┌─────────────────┴─────────────────┐

  └─────────────────────────────────────────────────────────┘
  
当你插入一个 USB 摄像头并点击“扫码”时，内部的完整协作顺序如下：

USBMonitor 率先工作：
检测到 USB 设备插入 ➔ 弹出 Android 系统权限框 ➔ 用户点击“允许” ➔ USBMonitor 拿到设备的通行凭证 UsbControlBlock。

UVCCamera 接入：
拿到通行凭证 ➔ 通过 JNI 唤醒底层的 libuvc ➔ 告诉 libuvc：“用这个凭证去和 USB 硬件建立连接，设置分辨率为 1080P”。

libuvc 狂飙数据：
向 USB 硬件发送指令 ➔ 硬件开始源源不断返回视频流 ➔ libuvc 解包数据 ➔ 传回给 UVCCamera 渲染到屏幕上，同时吐出 NV21 预览帧。

AndroidUSBCamera 统一调度：
在最外层打包好了上述所有步骤。你的代码只需要调用 AndroidUSBCamera 的接口，就能直接拿到解析好的图片和预览帧，轻松塞给扫码 SDK（如 ML Kit）。

libuvc 是协议本身；
USBMonitor + UVCCamera 是官方/原生的 Android 桥接层（但直接用需要你自己拼接这俩）
AndroidUSBCamera 是一站式打包好的集成方案，也是你开发项目时应该直接调用的库。

UVCCamera 依赖库 (libuvccamera)
│
├── Java 层 (包名 com.serenegiant.usb)
│   ├── USBMonitor.java       <-- 【在这个位置】负责 USB 设备插拔广播监听与权限申请
│   ├── UVCCamera.java        <-- 负责业务控制（打开/关闭预览、拍照、控制参数）
│   └── CameraDialog.java     <-- 选用的 UI 组件（弹框让用户选择哪个 USB 设备）
│
└── C/C++ 动态链接库 (.so 文件)
    ├── libusb                <-- 底层 USB 传输通信
    └── libuvc                <-- 底层 UVC 协议解析与视频流解包
	
USBMonitor 不是外来的第三方依赖，它原本就是 UVCCamera 项目的一部分；
libuvc 也已经编译成了 .so 动态库嵌入在内部；
因此，只要你引入了 AndroidUSBCamera 或 UVCCamera，上述所有的类和底层库全都已经内置，你直接调用即可。

$$\text{AndroidUSBCamera} \supset \text{UVCCamera} \supset (\text{USBMonitor} + \text{UVCCamera.java} + \text{libuvc} + \text{libusb})$$

如果你开发的应用是运行在以下设备上，方案一不仅可用，而且是首选的最佳方案：
定制的工控机、智能 POS 机、双屏收银机：国内如商米 (Sunmi)、拉卡拉、美团/客如云收银机等硬件厂商，其 Android 8.0+ / 10.0+ 的系统底层，官方均配置并开启了 ExternalCameraProvider（USB 摄像头服务）。
这种设备插入 USB 扫描头/外接摄像头后，系统直接将其映射为硬件摄像头。
你用 CameraX 的 LENS_FACING_EXTERNAL 即可直接拉起预览和扫码
Android 电视盒、智慧屏（如华为/小米智慧屏）、会议平板（如 MAXHUB）：这类设备通常需要外接 USB 摄像头来进行视频通话或人脸识别，系统底层对 UVC 摄像头的原生态支持非常完善。
部分国产平板（如华为/联手/小米平板）：在 Android 10 及以上系统的平板上，插入 OTG 外接摄像头，Camera2 通常能直接获取到该设备。

最理想方案：
每张试卷即将走纸前进行瞬时拍摄，这就要求硬件层面能够提供一个走纸信号，给到上层 APP，保持拍照时机和走纸频率保持一致。

退一步讲：
目前硬件层面无法提供这个信号，那么摄像头是间隔一定时间自动拍照，必然会出现两张试卷的卷头错开重叠的情况。
针对这种场景，拿到两个二维码，获取两个二维码的 Y 轴坐标，靠下的是当前试卷，靠上的是下一张试卷。
然后再根据靠下二维码的中心点向外裁剪，通过不断调试获取当前试卷的卷头图片。

解析：
卷头图片获取后，本地无法解析，需要上传服务器解析，再调接口获取解析后的数据，这中间也需要耗时。
卷头信息的 OCR 解析/复杂数据匹配依赖大模型或服务端高精度算法，本地轻量化模型无法保证 $99\%+$ 的准确率，因此必须上传服务器。
为了不阻塞前端走纸和连续拍照，APP 侧采用‘异步队列上传’架构——拍照和裁剪在本地毫秒级完成并排队，后台线程静默上传解析，确保走纸流程不卡顿。

[走纸拍照] ──► [MLKit二维码识别 + 坐标推算] ──► [本地BitmapRegionDecoder裁剪] 
  │ (毫秒级，本地完成)
  ▼
[存入本地上传队列] ──► (后台异步线程) ──► [上传服务器 OCR 识别] ──► [调接口接收结果]

本地采集耗时（APP 侧）： 约 $50 \sim 150\text{ ms}$（二维码识别 + 坐标计算 + 区域裁剪），完全能跟上连续走纸拍摄的频率。
云端解析耗时（服务端）： 受网络传输与服务器 OCR 处理影响，单张耗时约 $500 \sim 1500\text{ ms}$。

实时预览 (15~30 FPS)：
UsbScanManager 每秒在处理 15-30 帧 图像。
在动态走纸或视频流中，哪怕有 10 帧因为光线反射、运动模糊或角度倾斜导致 ML Kit 解析失败，只要有 1 帧 角度合适、光线均匀，瞬间就通过 addOnSuccessListener 触发回调了。你感知到的是“扫码成功”。

拍照 (静态 1 帧)：
CaptureFragment.capture() 只抓取了按下快门或触发时刻的 唯一一张照片。
如果这张静态照片恰好存在模糊、曝光过度（摄像头闪光/反光）、畸变或处于移动拉丝状态，ML Kit 就彻底没有第二次机会了。

直接扫码正常而拍照静态图检测不到的核心原因在于：静态 JPEG 图像未经方向校正（旋转角丢失/倒置）、全尺寸分辨率过高导致 ML Kit 降采样细节丢失，以及没有像预览流那样进行“下采样 + 多角度/方向强制纠正”。
